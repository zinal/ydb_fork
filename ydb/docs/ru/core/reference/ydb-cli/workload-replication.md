# Replication нагрузка

Нагрузка для проверки [асинхронной репликации](../../concepts/async-replication.md) строковых таблиц. Команда создаёт набор исходных таблиц, заполняет их и затем пишет в них многотабличные транзакции. По этим записям на базе-источнике возникает поток изменений, который забирает репликация.

Экземпляр асинхронной репликации создаёт пользователь после начального заполнения и до запуска записи. Начальные строки попадают в реплику через [первоначальное сканирование](../../concepts/async-replication.md#initial-scan), а транзакции `run` дают [репликацию изменений](../../concepts/async-replication.md#replication-of-changes). Команда пишет только в базу-источник.

## Порядок запуска {#flow}

```bash
{{ ydb-cli }} workload replication init [options...]
{{ ydb-cli }} workload replication import [options...]
# здесь пользователь создаёт экземпляр асинхронной репликации
{{ ydb-cli }} workload replication run [options...]
{{ ydb-cli }} workload replication clean [options...]
```

1. `init` создаёт каталог и пустые строковые таблицы.
2. `import` записывает в каждую таблицу ровно **Q** строк. Q задаётся параметром `--rows`.
3. Пользователь создаёт экземпляр асинхронной репликации на этот каталог выражением [CREATE ASYNC REPLICATION](../../yql/reference/syntax/create-async-replication.md).
4. `run` в течение заданного времени выполняет транзакции записи.
5. `clean` удаляет таблицы нагрузки и их каталог. Перед `clean` пользователь удаляет экземпляр репликации: пока репликация удерживает потоки изменений этих таблиц, удаление может завершиться ошибкой сервера.

{% note info %}

Каталог `--path` содержит только таблицы этой нагрузки. Репликация каталога захватывает все строковые таблицы, которые лежат в нём на момент создания экземпляра.

{% endnote %}

## Схема таблиц {#schema}

Все таблицы — строковые. Они создаются в каталоге `--path` (по умолчанию `replication`). Вторичные индексы и настройки партиционирования описаны ниже.

Колонки первичного ключа объявляются `NOT NULL`. Остальные колонки допускают `NULL`; каждая запись кладёт в них конкретное значение.

В первичном ключе строковой таблицы допустимы сравнимые типы, которые хранилище принимает в колонке. Нагрузка ставит в ключ типы из таблиц ниже. `Interval` и `Interval64` в них входят: для обоих задано сравнение ключей, и таблица с `Interval` в составе первичного ключа создаётся. Типы `TzDate`, `TzDatetime`, `TzTimestamp`, `TzDate32`, `TzDatetime64` и `TzTimestamp64` в колонках строковых таблиц не хранятся, поэтому в схеме их нет ни в ключе, ни в значениях. `Float`, `Double`, `Json`, `JsonDocument` и `Yson` в первичном ключе не используются; они есть среди колонок значений. `Uuid` в первичном ключе требует одноимённую возможность сервера; в конфигурации по умолчанию она включена. Хранилище также принимает в ключе `DyNumber` и сравнимые типы PostgreSQL; колонок этих типов в схеме нет.

Таблицы делятся на обычные и широкие. Обычная таблица хранит узкие значения и состоит из 10 колонок разных типов; колонки типов `Utf8`, `String`, `Json`, `JsonDocument` и `Yson` в ней заполнены узко. Широкая таблица состоит из 30 колонок разных типов, ещё одной текстовой колонки среднего заполнения и ещё одной текстовой колонки широкого заполнения.

### Номер строки {#row-number}

У каждой строки таблицы есть номер `n` — целое от 0 и выше. Первичный ключ однозначно вычисляется из `n`, разным номерам соответствуют разные ключи. После `import` в таблице лежат номера `0 .. Q-1`. Дальше `run` дописывает следующие номера.

### Поле seqno {#seqno}

В каждой таблице есть колонка `seqno Uint64 NOT NULL`. В первичный ключ она не входит. Колонка `seq` у узкого ключа — это номер строки `n`. Колонка `seqno` — номер операции, один на все таблицы сразу.

Все строки всех таблиц, которые одна транзакция вставляет или изменяет, записываются с одним и тем же `seqno`.

Номер выдаёт атомарный счётчик транзакций в процессе команды. Счётчик увеличивается в момент формирования транзакции. Повтор этой транзакции то же значение сохраняет.

При первоначальной загрузке `import` у каждой записанной строки `seqno` равен 0. Загрузка счётчик не двигает.

При запуске `run` счётчик устанавливается в текущее unix-время в микросекундах: целое число микросекунд UTC с 1970-01-01. Первая транзакция этого запуска получает именно его, каждая следующая новая транзакция — на единицу больше. Новый запуск `run` снова ставит счётчик в unix-время своего старта, тоже в микросекундах.

### Композитный ключ узкого типа {#composite-key}

Если различных значений типа меньше 2^32, одной колонки этого типа мало: после исчерпания диапазона вставить новую строку нельзя. Первичный ключ такой таблицы — `(pk <тип>, seq Uint64)`. Второй компонент всегда `Uint64` и равен номеру `n`. Первая колонка пробегает весь диапазон типа: `pk` получается из `n % <размер диапазона>`.

К узким типам относятся `Bool` (2 значения), `Int8` и `Uint8` (256), `Int16` и `Uint16` (65536), `Date` (дни от 1970-01-01 до 2105-12-31) и `Decimal(1, 0)` (значения от −9 до 9).

Остальные ключевые типы вмещают не меньше 2^32 значений. У них первичный ключ — одна колонка `pk`, и она монотонно растёт вместе с `n`.

### Обычные таблицы {#ordinary-tables}

Обычные таблицы — это 23 таблицы первичных ключей. В каждой ровно 10 колонок. Колонки `seq` и `seqno` обе имеют тип `Uint64`: первая есть только у композитного ключа и хранит номер строки, вторая есть у всех таблиц и хранит номер операции. Остальные колонки одной таблицы имеют разные типы. Если тип ключа совпадает с типом одной из колонок значений, в таблице две колонки этого типа.

Для одноколоночного ключа номер `n` должен помещаться в тип. У `Int32` это значения до 2^31−1, у `Datetime`, `Timestamp` и `Interval` — до верхней границы типа.

### Заполнение текстовых колонок {#text-size}

К текстовым типам здесь относятся `Utf8`, `String`, `Json`, `JsonDocument` и `Yson`.

| Класс | Размер |
| --- | --- |
| узкий | от 0 до 100 байт включительно |
| средний | от 100 до 500 байт включительно, длина случайная |
| широкий | от 1000 до 5000 байт включительно, длина случайная |

Размер считается так:

* `Utf8` — число байт текста. Генератор пишет печатный ASCII, поэтому число байт совпадает с числом символов.
* `String` — число байт. Содержимое случайное и может быть любой байтовой последовательностью.
* `Json`, `JsonDocument` и `Yson` — число байт текста, который клиент передаёт параметром. Документ корректный. Для узкого класса нижняя граница — длина самого короткого корректного значения: 2 байта (`{}`) у `Json` и `JsonDocument`, 1 байт (`#`) у `Yson`. `JsonDocument` в `c_medium` и `c_wide` получает текст того же размера, что `Json` этого класса. Сервер хранит `JsonDocument` в бинарном виде, и размер на диске может отличаться от размера текста.

Узкий класс для `String` и `Utf8` включает пустое значение.

В каталоге 28 таблиц: 23 обычные и 5 широких.

## Индексы и партиционирование {#indexes}

На колонку `seqno` каждой таблицы создаётся синхронный вторичный индекс `seqno_idx`:

```yql
INDEX seqno_idx GLOBAL SYNC ON (seqno)
```

На колонку `seq` создаётся такой же индекс `seq_idx`. Колонка `seq` есть только у таблиц с композитным ключом: `pk_bool`, `pk_int8`, `pk_uint8`, `pk_int16`, `pk_uint16`, `pk_date`, `pk_decimal_narrow`. У остальных таблиц индекса по `seq` нет.

Для каждой таблицы и каждого из этих индексов включено автоматическое партиционирование по размеру и по нагрузке. Минимальное и максимальное число партиций задаётся параметрами `init` и по умолчанию равно 1000 и 1100:

```yql
AUTO_PARTITIONING_BY_SIZE = ENABLED,
AUTO_PARTITIONING_BY_LOAD = ENABLED,
AUTO_PARTITIONING_MIN_PARTITIONS_COUNT = 1000,
AUTO_PARTITIONING_MAX_PARTITIONS_COUNT = 1100
```

У таблицы эти параметры стоят в `WITH` при создании. Если первая колонка первичного ключа имеет тип `Uint32` или `Uint64`, дополнительно задаётся `UNIFORM_PARTITIONS`, равный минимуму: столько партиций таблица получает сразу. Для другого типа первой колонки равномерное начальное разбиение недоступно, и таблица создаётся с одной партицией; дальше число партиций меняется автоматически и не выходит за заданные минимум и максимум.

Параметры партиционирования индекса при создании индекса не задаются. `init` создаёт индекс, затем выполняет `ALTER TABLE … ALTER INDEX … SET` с теми же четырьмя параметрами. `UNIFORM_PARTITIONS` для индекса не устанавливается.

Если минимум больше максимума, `init` завершается ошибкой параметра и таблицы не создаёт.

## Начальное заполнение {#import}

`import` вставляет в каждую таблицу строки с номерами `0 .. Q−1`. Ключ строки вычисляется по таблице выше. У всех этих строк `seqno` равен 0. Пачка загрузки идемпотентна: повтор пишет те же ключи тем же `UPSERT` с `seqno` 0.

Команда завершается после фиксации всех этих строк. Строки одной таблицы могут записываться несколькими транзакциями; размер пачки на сценарий `run` не влияет.

Повторный `import` при уже записанных строках завершает команду с ошибкой, не переписывая таблицу. Рабочий порядок — один `import` после `init`.

При Q = 0 таблицы остаются пустыми. Первые транзакции `run` тогда состоят из вставок, пока в таблице не появится хотя бы одна зафиксированная строка.

## Граница номеров {#boundary}

Изменение адресует уже существующую строку. Для этого по каждой таблице известна граница: максимальный номер, для которого зафиксированы и этот номер, и все меньшие. Существующие номера — это `0, 1, …, boundary`. Следующая вставка получает `boundary + 1`.

### Чтение границы на старте `run` {#boundary-read}

Перед первой транзакцией команда один раз читает границу каждой таблицы из базы.

Для одноколоночного ключа, который растёт вместе с номером, читается максимальное значение ключевой колонки. В обычных таблицах эта колонка называется `pk`, в широких — `id`:

```sql
SELECT <ключевая колонка> FROM `<таблица>` ORDER BY <ключевая колонка> DESC LIMIT 1
```

Обычные таблицы этого запроса: `pk_int32`, `pk_int64`, `pk_uint32`, `pk_uint64`, `pk_decimal`, `pk_decimal_wide`, `pk_date32`, `pk_datetime`, `pk_datetime64`, `pk_timestamp`, `pk_timestamp64`, `pk_interval`, `pk_interval64`, `pk_uuid`. Широкие: `wide_utf8`, `wide_string`, `wide_json`, `wide_json_doc`, `wide_yson`.

Номер восстанавливается из найденного ключа обратным правилом раздела [обычных таблиц](#ordinary-tables): для целых, дат, интервалов и `Decimal` это сам числовой компонент ключа, для `Uuid` — младшие 8 байт как big-endian, для широких таблиц номер равен `id`. Пустой результат означает пустую таблицу, границы нет.

Для композитного ключа монотонная компонента — `seq`, а `pk` по диапазону циклически повторяется. Максимум пары `(pk, seq)` в лексикографическом порядке не равен максимальному номеру, поэтому граница читается по `seq`:

```sql
SELECT seq FROM `<таблица>` ORDER BY seq DESC LIMIT 1
```

Найденное `seq` и есть максимальный номер.

Для `pk_string` и `pk_utf8` ключ является хешем. `ORDER BY pk` показывает максимум хеша, а не максимум номера. Число уже записанных строк совпадает с числом номеров `0 .. boundary`, поэтому граница читается так:

```sql
SELECT COUNT(*) FROM `<таблица>`
```

Если запрос вернул `C`, максимальный номер равен `C − 1`, а следующий свободный номер равен `C`. Ноль означает пустую таблицу.

Это чтение верно, пока в таблице лежат только строки этой нагрузки и их номера образуют сплошной префикс `0 .. boundary`. Как этот префикс сохраняется, описано ниже.

### Ведение границы во время `run` {#boundary-maintain}

Граница хранится в памяти процесса и двигается вперёд, когда транзакция с новыми номерами успешно фиксируется.

Новые номера одной таблицы резервирует и фиксирует не больше одной транзакции одновременно. Транзакция, которой нужны вставки в несколько таблиц, захватывает эти таблицы в порядке имён и держит захват до конца фиксации, поэтому взаимной блокировки между пользователями нет. Повторно исполняемая транзакция использует уже зарезервированные номера. Номер входит в границу только после успешной фиксации. Пока транзакция не зафиксирована, изменение эти номера не выбирает.

Отсюда зафиксированные номера таблицы всегда идут сплошняком от 0 до текущей границы. Следующий запуск `run` тем же запросом `ORDER BY … DESC LIMIT 1` или `COUNT(*)` читает ту же границу. Обрыв процесса до фиксации откатывает незавершённую транзакцию на сервере, дырки в префиксе не остаётся.

Изменение выбирает номер равномерно среди `0 .. boundary` включительно, по состоянию границы на начало транзакции. В одной транзакции номера изменения различны, если их не больше, чем `boundary + 1`. Если запланированных изменений больше, чем уже существующих строк, лишние изменения становятся вставками и получают следующие номера.

## Транзакции {#transactions}

Каждая транзакция — одна атомарная запись в сериализуемом режиме. В ней вставки новых строк и изменения уже существующих. Удалений нет, состав колонок не меняется.

Число затронутых таблиц **M** выбирается равномерно от 1 до числа таблиц в каталоге. Затем равномерно выбирается случайное подмножество из M различных таблиц.

В каждую выбранную таблицу транзакция пишет **R** строк. R выбирается равномерно от 1 до **K** включительно. K задаётся параметром `--max-records`. Из этих R строк `floor(R / 2)` планируются как вставки, остальные — как изменения. При R = 1 это одно изменение. При R = 2 — одна вставка и одно изменение. Если существующих строк меньше, чем запланировано изменений, недостающие изменения выполняются как вставки. В пустой таблице все R строк — вставки.

Вставка заполняет все колонки и выполняется `UPSERT`. Изменение каждой строки выполняется оператором `UPDATE` и задаёт новые значения у 1, 2 или 3 колонок этой строки. Число колонок выбирается равномерно. В набор всегда входит `seqno` с номером операции этой транзакции; остальные места занимают случайные колонки со значениями, не входящие в первичный ключ. Условие `WHERE` содержит все колонки первичного ключа и сравнивает их на равенство: для одноколоночного ключа это `pk`, для композитного — `pk` и `seq`.

Транзакция идемпотентна и выполняется в обработчике повторов клиента с признаком идемпотентности. До первой попытки фиксируются первичные ключи, выбранные для изменения колонки, их новые значения и `seqno`. Каждая попытка отправляет те же операторы с теми же параметрами. Повтор `UPSERT` после фиксации, ответ на которую клиент не увидел, записывает те же строки и не завершается конфликтом первичного ключа. Повтор `UPDATE` снова записывает те же колонки по тому же полному первичному ключу. Обработчик повторяет статусы, которые безопасно повторять для идемпотентной операции, в том числе когда исход попытки неизвестен. На повторе не выделяются ни новые номера строк, ни новый `seqno`, ни другой набор колонок.

Успех транзакции считается после этого обработчика. Повторяемые сбои в частоту ошибок не попадают, если итоговая попытка успешна. В частоту ошибок попадает транзакция, у которой последняя попытка завершилась неуспехом. Одна такая транзакция — одна ошибка, независимо от числа таблиц внутри неё. Её номера строк в границу не входят, её `seqno` повторно не используется. Захват таблиц после неуспеха снимается, и следующая вставка в ту же таблицу снова берёт номера строк начиная с `boundary + 1`.

## Параллелизм {#concurrency}

`--users` задаёт число параллельных пользователей. Значение по умолчанию — 1. Каждый пользователь в цикле выполняет одну транзакцию, ждёт `--pause` и начинает следующую. Пауза одинакова после успеха и после ошибки. Ожидание паузы асинхронное.

Верхняя граница одновременных транзакций равна числу пользователей. Пул сессий клиента рассчитан на это число. Транзакции, которые вставляют строки в одну и ту же таблицу, проходят через неё по очереди. Транзакции с непересекающимися наборами таблиц идут одновременно. Изменения уже зафиксированных номеров друг друга не блокируют.

`--threads` задаёт число потоков клиентского пула, на котором исполняются завершения асинхронных операций. Значение по умолчанию — 0: пул адаптивный, его размер выбирает клиент. Положительное значение фиксирует размер пула. Сетевые потоки драйвера остаются в значении по умолчанию клиента.

`--seconds` ограничивает время запуска. По истечении времени новые транзакции не начинаются, уже отправленные дожидаются своего таймаута. Пауза прерывается вместе с остановкой. Захват таблиц снимается до выхода, в том числе если транзакция так и не зафиксировалась.

`--seed` фиксирует генератор случайных чисел: выбор таблиц, число строк R, выбор номеров для изменения, длины и содержимое значений. При нескольких пользователях зерно задаёт решения каждого пользователя, но не порядок, в котором их транзакции перемежаются. Если параметр не указан, зерно берётся из текущего времени. Номера новых строк от зерна не зависят: их выдаёт граница таблицы.

## Вывод {#output}

Раз в `--window` секунд (по умолчанию раз в секунду) на стандартный вывод печатается одна строка:

```text
elapsed_s=<секунды> tx_per_s=<частота> errors_per_s=<частота> tx=<число> errors=<число>
```

`tx` и `errors` — счётчики за это окно. Частоты — эти счётчики, делённые на длину окна, с одним знаком после точки.

После остановки печатается итог за всё время запуска в той же форме: `tx` и `errors` суммарные, частоты посчитаны по полной длительности.

С `--verbose` (глобальный параметр `-v`) каждая ошибка дополнительно печатается на стандартный вывод ошибок:

```text
error status=<код статуса> issues=<текст сообщений>
```

Текст запроса в это сообщение не входит. Без `--verbose` печатаются только частоты и счётчики.

Ненулевой код возврата `run` остаётся за ошибками запуска: нет таблиц, неверные параметры, обрыв самого запуска. Ошибки отдельных транзакций код возврата не меняют, они видны в `errors` и, при `--verbose`, в текстах ошибок.

## Параметры {#options}

Общие для `init`, `import`, `run` и `clean`:

| Параметр | Описание | По умолчанию |
| --- | --- | --- |
| `--path` | Каталог таблиц нагрузки в базе-источнике | `replication` |

`init`:

| Параметр | Описание | По умолчанию |
| --- | --- | --- |
| `--min-partitions` | Минимум партиций таблицы и каждого вторичного индекса, `AUTO_PARTITIONING_MIN_PARTITIONS_COUNT` | `1000` |
| `--max-partitions` | Максимум партиций таблицы и каждого вторичного индекса, `AUTO_PARTITIONING_MAX_PARTITIONS_COUNT` | `1100` |

`import`:

| Параметр | Описание | По умолчанию |
| --- | --- | --- |
| `--rows` | Q, число строк начального заполнения в каждую таблицу | `1000` |

`run`:

| Параметр | Описание | По умолчанию |
| --- | --- | --- |
| `--seconds`, `-s` | Длительность записи, секунды | `60` |
| `--users` | Число параллельных пользователей | `1` |
| `--max-records` | K, верхняя граница числа строк в одну таблицу внутри транзакции. Фактическое число случайно от 1 до K | `10` |
| `--pause` | Пауза пользователя между транзакциями. Обычное число без суффикса читается как миллисекунды | `100ms` |
| `--threads` | Потоки клиентского пула. 0 — адаптивный пул | `0` |
| `--window` | Окно вывода частот, секунды | `1` |
| `--seed` | Зерно генератора. Без параметра зерно берётся из текущего времени | — |
| `--client-timeout` | Транспортный таймаут. Обычное число без суффикса — миллисекунды | `10s` |
| `--operation-timeout` | Таймаут операции | `5s` |
| `--cancel-after` | Таймаут отмены операции | `5s` |

Таймауты рассчитаны на транзакцию, которая пишет несколько таблиц, включая строки в несколько килобайт.

## Пример {#example}

```bash
{{ ydb-cli }} workload replication init --path replication
{{ ydb-cli }} workload replication import --path replication --rows 1000
```

Дальше на базе-приёмнике пользователь создаёт репликацию каталога. Параметры соединения и аутентификации описаны в [CREATE ASYNC REPLICATION](../../yql/reference/syntax/create-async-replication.md). Команда нагрузки этот запрос не выполняет:

```yql
CREATE ASYNC REPLICATION replication_workload
FOR `replication` AS `replication_replica`
WITH (
    CONNECTION_STRING = 'grpcs://<источник>:2135/?database=<база-источник>',
    TOKEN_SECRET_PATH = '<секрет>'
);
```

После создания экземпляра запускается запись, при необходимости с текстом ошибок:

```bash
{{ ydb-cli }} -v workload replication run \
    --path replication \
    --users 4 \
    --max-records 10 \
    --pause 100ms \
    --seconds 300
```

Снятие нагрузки:

```bash
{{ ydb-cli }} workload replication clean --path replication
```

## Что остаётся пользователю {#scope}

Пользователь создаёт, описывает, завершает и удаляет экземпляр асинхронной репликации. Команда не ждёт окончания первоначального сканирования и не читает лаг. Совпадение реплики с источником проверяется снаружи.
