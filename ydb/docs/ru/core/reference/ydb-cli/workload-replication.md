# Replication нагрузка

Нагрузка для проверки [асинхронной репликации](../../concepts/async-replication.md) строковых таблиц. Команда создаёт набор исходных таблиц, заполняет их и затем пишет в них многотабличные транзакции. По этим записям на базе-источнике возникает поток изменений, который забирает репликация.

Экземпляр асинхронной репликации команда не создаёт, не изменяет и не удаляет. Его создаёт пользователь после начального заполнения и до запуска записи. Так начальные строки попадают в реплику через [первоначальное сканирование](../../concepts/async-replication.md#initial-scan), а транзакции `run` проверяют уже [репликацию изменений](../../concepts/async-replication.md#replication-of-changes).

Команда пишет только в базу-источник. Чтение реплик, лаг и сравнение содержимого остаются на стороне пользователя.

## Постановка {#scenario}

Нагрузка работает с фиксированным набором из **30 строковых таблиц** в одном каталоге. Тридцать таблиц закрывают требование «от 10 разных таблиц» и одновременно дают отдельную таблицу на каждый тип, который можно поставить в первичный ключ, отдельные варианты `Decimal` и три класса размера текстовых и JSON-колонок.

Один запуск проходит четыре шага:

1. `init` создаёт каталог и 30 пустых строковых таблиц.
2. `import` записывает в каждую таблицу ровно **Q** строк. Q задаётся параметром `--rows`.
3. Пользователь сам создаёт экземпляр асинхронной репликации на этот каталог (или на перечисленные таблицы) выражением [CREATE ASYNC REPLICATION](../../yql/reference/syntax/create-async-replication.md).
4. `run` в течение заданного времени выполняет транзакции записи.

Транзакция устроена так:

* число затронутых таблиц **M** выбирается равномерно из диапазона от 1 до **N**, где N — число таблиц набора (30);
* затем равномерно выбирается случайное подмножество из M различных таблиц;
* в каждую выбранную таблицу транзакция пишет **R** строк, где R выбирается равномерно из диапазона от 1 до **K** включительно; K задаётся параметром `--max-records`;
* из этих R строк `floor(R / 2)` вставляются как новые строки, остальные `R - floor(R / 2)` изменяют уже существующие строки начального заполнения;
* при R = 1 получается одно изменение существующей строки; при R = 2 — одна вставка и одно изменение.

Несколько пользователей выполняют такие транзакции параллельно. У каждого пользователя не больше одной транзакции в полёте. После завершения транзакции пользователь ждёт паузу и начинает следующую. Пауза по умолчанию — 100 миллисекунд, параметр `--pause`.

Запись идёт через асинхронный интерфейс клиента. Ожидание ответа сервера и пауза не блокируют поток. Число потоков клиентского пула выбирается автоматически и при необходимости задаётся параметром `--threads`.

Пока `run` работает, на стандартный вывод печатается частота успешных транзакций и частота ошибок. В режиме подробного вывода (`-v`, `--verbose`) на стандартный вывод ошибок дополнительно печатается текст каждой ошибки.

## Порядок запуска {#flow}

```bash
{{ ydb-cli }} workload replication init [options...]
{{ ydb-cli }} workload replication import [options...]
# здесь пользователь создаёт экземпляр асинхронной репликации
{{ ydb-cli }} workload replication run [options...]
{{ ydb-cli }} workload replication clean [options...]
```

`clean` удаляет только таблицы нагрузки и их каталог. Перед `clean` пользователь сам удаляет экземпляр репликации: пока репликация удерживает потоки изменений этих таблиц, удаление может завершиться ошибкой сервера.

{% note info %}

Каталог `--path` должен содержать только таблицы этой нагрузки. Репликация каталога захватывает все строковые таблицы, которые лежат в нём на момент создания экземпляра.

{% endnote %}

## Схема таблиц {#schema}

Все таблицы — обычные строковые таблицы без вторичных индексов и без явных настроек партиционирования. Они создаются в каталоге `--path` (по умолчанию `replication`).

Колонки первичного ключа объявляются `NOT NULL`. Остальные колонки допускают `NULL`, но генератор всегда записывает в них конкретное значение: отдельной проверки репликации `NULL` эта нагрузка не делает.

Типы, которые нельзя хранить в колонке таблицы или нельзя поставить в первичный ключ, в схему не входят. Это контейнеры YQL, `Float`, `Double`, `Json`, `JsonDocument` и `Yson` в роли ключа, типы `TzDate`, `TzDatetime`, `TzTimestamp`, тип `DyNumber` и типы PostgreSQL.

### Таблицы первичных ключей {#pk-tables}

На каждый допустимый тип первичного ключа приходится отдельная таблица. Узкий домен, в который не помещается длинная серия новых ключей, дополняется второй ключевой колонкой `seq Uint64`. Первой колонкой ключа остаётся проверяемый тип: по ней строятся порядок строк и границы партиций.

В такой таблице одна неключевая колонка `marker Uint64`. Вставка и изменение записывают в неё новое значение, поэтому в потоке изменений у строки меняется образ, а не только факт обращения.

| Таблица | Первичный ключ | Как из номера строки `i` получается ключ |
| --- | --- | --- |
| `pk_bool` | `(pk Bool, seq Uint64)` | `pk = (i % 2 = 1)`, `seq = i` |
| `pk_int8` | `(pk Int8, seq Uint64)` | `pk` пробегает весь диапазон `Int8`, `seq = i` |
| `pk_int16` | `(pk Int16, seq Uint64)` | `pk` пробегает весь диапазон `Int16`, `seq = i` |
| `pk_int32` | `(pk Int32)` | `pk = i` |
| `pk_int64` | `(pk Int64)` | `pk = i` |
| `pk_uint8` | `(pk Uint8, seq Uint64)` | `pk = i % 256`, `seq = i` |
| `pk_uint16` | `(pk Uint16, seq Uint64)` | `pk = i % 65536`, `seq = i` |
| `pk_uint32` | `(pk Uint32)` | `pk = i` |
| `pk_uint64` | `(pk Uint64)` | `pk = i` |
| `pk_decimal` | `(pk Decimal(22, 9))` | штатный `Decimal`: целая часть равна `i`, девять дробных знаков нули |
| `pk_decimal_narrow` | `(pk Decimal(1, 0), seq Uint64)` | `pk` пробегает весь диапазон `Decimal(1, 0)`, `seq = i` |
| `pk_decimal_wide` | `(pk Decimal(35, 0))` | максимально широкий целочисленный `Decimal`: `pk = i` |
| `pk_string` | `(pk String)` | байтовая строка десятичной записи `i` |
| `pk_utf8` | `(pk Utf8)` | текстовая десятичная запись `i` |
| `pk_uuid` | `(pk Uuid)` | UUID с корректными битами версии и варианта, номер `i` записан в младшие байты |
| `pk_date` | `(pk Date, seq Uint64)` | `pk` циклически пробегает допустимый диапазон `Date`, `seq = i` |
| `pk_date32` | `(pk Date32)` | сдвиг в днях от начала диапазона на `i` |
| `pk_datetime` | `(pk Datetime)` | `i` секунд от начала диапазона |
| `pk_datetime64` | `(pk Datetime64)` | `i` секунд от начала диапазона |
| `pk_timestamp` | `(pk Timestamp)` | `i` микросекунд от начала диапазона |
| `pk_timestamp64` | `(pk Timestamp64)` | `i` микросекунд от начала диапазона |
| `pk_interval` | `(pk Interval)` | интервал `i` микросекунд |
| `pk_interval64` | `(pk Interval64)` | интервал `i` микросекунд |
| `pk_tz_date32` | `(pk TzDate32)` | та же дата, что у `Date32`, таймзона `Europe/Moscow` |
| `pk_tz_datetime64` | `(pk TzDatetime64)` | тот же момент, что у `Datetime64`, таймзона `Europe/Moscow` |
| `pk_tz_timestamp64` | `(pk TzTimestamp64)` | тот же момент, что у `Timestamp64`, таймзона `Europe/Moscow` |

`Decimal(22, 9)` — штатная параметризация. `Decimal(1, 0)` — самая узкая: один десятичный разряд и ни одного дробного. `Decimal(35, 0)` — максимальная точность 35 при нулевом масштабе. Номера строк, которые порождает эта нагрузка, укладываются в точность 22 и 35. Для одноколоночного ключа номер `i` должен помещаться в сам тип: у `Int32` это значения до 2^31−1, у `Datetime` и `Timestamp` — до верхней границы типа. Практически Q и число вставок за запуск остаются далеко внутри этих границ.

Широкие текст, байты и JSON в эту таблицу не кладутся: одна транзакция может затронуть все 30 таблиц сразу, и широкий образ на каждой строке раздул бы запрос.

### Таблицы размера значения {#payload-tables}

Три таблицы несут колонки текст (`Utf8`), байты (`String`), `Json` и `JsonDocument`. У каждой таблицы свой класс размера. Первичный ключ — `(id Uint64)`.

| Таблица | Класс | Размер значения |
| --- | --- | --- |
| `payload_narrow` | узкий | от 0 до 100 байт включительно |
| `payload_medium` | средний | от 100 до 500 байт включительно, длина случайная |
| `payload_wide` | широкий | от 1000 до 5000 байт включительно, длина случайная |

Колонки во всех трёх таблицах: `utf8 Utf8`, `bin String`, `json Json`, `json_doc JsonDocument`.

Размер считается так:

* `Utf8` — число байт текста. Генератор пишет печатный ASCII, поэтому число байт совпадает с числом символов.
* `String` — число байт. Содержимое случайное и может быть любой байтовой последовательностью.
* `Json` и `JsonDocument` — число байт текста JSON, который клиент передаёт параметром. Документ всегда корректный. Для узкого класса нижняя граница поднимается до 2 байт (`{}`), потому что более короткий JSON не существует. `JsonDocument` получает тот же текст: сервер хранит его в бинарном виде, и размер на диске может отличаться от размера текста.

Узкий класс для `String` и `Utf8` включает пустое значение.

## Начальное заполнение {#import}

`import` вставляет в каждую из 30 таблиц строки с номерами `i` от 0 до Q−1 включительно. Ключ строки полностью определяется номером по таблице из раздела выше.

Команда завершается после того, как все эти строки зафиксированы. Строки одной таблицы могут записываться несколькими транзакциями; размер пачки — деталь реализации и на сценарий `run` не влияет.

Повторный `import` в непустые таблицы конфликтует по первичному ключу и завершает команду с ошибкой. Рабочий порядок — один `import` после `init`.

При Q = 0 таблицы остаются пустыми. Тогда на шаге `run` операций изменения нет: все R строк транзакции становятся вставками.

## Транзакции режима run {#transactions}

Каждая транзакция — одна атомарная запись в сериализуемом режиме. В ней только вставки новых строк и изменения уже существующих. Удалений нет, состав колонок не меняется.

Для каждой выбранной таблицы:

* новые строки получают следующие номера после уже выданных: общий для всех пользователей счётчик таблицы начинается с Q;
* номер, выданный неуспешной транзакции, повторно не используется, поэтому в ряду ключей допустимы пропуски;
* изменяемые строки равномерно выбираются среди начальных ключей `i` от 0 до Q−1;
* вставка заполняет все колонки;
* изменение переписывает все неключевые колонки и не меняет первичный ключ.

Начальные ключи не зависят от гонок между пользователями: их записал `import`, и `run` их не удаляет. Новые строки других транзакций в мишень изменения не входят.

Успех транзакции считается после повторных попыток клиента. Повторяемые сбои (`OVERLOADED`, обрыв транспорта и другие статусы, которые клиент переживает сам) в частоту ошибок не попадают, если итоговая попытка успешна. В частоту ошибок попадает транзакция, у которой последняя попытка завершилась неуспехом. Одна такая транзакция — одна ошибка, независимо от числа таблиц внутри неё.

## Параллелизм {#concurrency}

`--users` задаёт число параллельных пользователей. Значение по умолчанию — 1. Каждый пользователь в цикле выполняет одну транзакцию, ждёт `--pause` и начинает следующую. Пауза одинакова после успеха и после ошибки, поэтому серия ошибок не превращается в плотный цикл. Ожидание паузы асинхронное.

Верхняя граница одновременных транзакций равна числу пользователей. Пул сессий клиента рассчитан на это число.

`--threads` задаёт число потоков клиентского пула, на котором исполняются завершение асинхронных операций. Значение по умолчанию — 0: пул адаптивный, его размер выбирает клиент. Положительное значение фиксирует размер пула. Сетевые потоки драйвера остаются в значении по умолчанию клиента.

`--seconds` ограничивает время запуска. По истечении времени новые транзакции не начинаются, уже отправленные дожидаются своего таймаута. Пауза прерывается вместе с остановкой.

`--seed` фиксирует генератор случайных чисел: выбор таблиц, число строк R, выбор изменяемых ключей, длины и содержимое значений. При нескольких пользователях зерно задаёт решения каждого пользователя, но не порядок, в котором их транзакции перемежаются. Если параметр не указан, зерно берётся из текущего времени.

## Вывод {#output}

Раз в `--window` секунд (по умолчанию раз в секунду) на стандартный вывод печатается одна строка:

```text
elapsed_s=<секунды> tx_per_s=<частота> errors_per_s=<частота> tx=<число> errors=<число>
```

`tx` и `errors` — счётчики за это окно. Частоты — эти счётчики, делённые на длину окна, с одним знаком после точки.

После остановки печатается итог за всё время запуска в той же форме: `tx` и `errors` суммарные, частоты посчитаны по полной длительности.

С `--verbose` (глобальный параметр `-v`) каждая ошибка дополнительно печатается на стандартный вывод ошибок:

```text
error status=<код статуса> issues=<текст сообщений>
```

Текст запроса в это сообщение не входит. Без `--verbose` печатаются только частоты и счётчики.

Ненулевой код возврата `run` оставляет за ошибками запуска: нет таблиц, неверные параметры, обрыв самого запуска. Ошибки отдельных транзакций код возврата не меняют, они видны в `errors` и, при `--verbose`, в текстах ошибок.

## Параметры {#options}

Общие для `init`, `import`, `run` и `clean`:

| Параметр | Описание | По умолчанию |
| --- | --- | --- |
| `--path` | Каталог таблиц нагрузки в базе-источнике | `replication` |

`import`:

| Параметр | Описание | По умолчанию |
| --- | --- | --- |
| `--rows` | Q, число строк начального заполнения в каждую таблицу | `1000` |

`run`:

| Параметр | Описание | По умолчанию |
| --- | --- | --- |
| `--seconds`, `-s` | Длительность записи, секунды | `60` |
| `--users` | Число параллельных пользователей | `1` |
| `--max-records` | K, верхняя граница числа строк в одну таблицу внутри транзакции. Фактическое число случайно от 1 до K | `10` |
| `--pause` | Пауза пользователя между транзакциями. Обычное число без суффикса читается как миллисекунды | `100ms` |
| `--threads` | Потоки клиентского пула. 0 — адаптивный пул | `0` |
| `--window` | Окно вывода частот, секунды | `1` |
| `--seed` | Зерно генератора. Без параметра зерно берётся из текущего времени | — |
| `--client-timeout` | Транспортный таймаут. Обычное число без суффикса — миллисекунды | `10s` |
| `--operation-timeout` | Таймаут операции | `5s` |
| `--cancel-after` | Таймаут отмены операции | `5s` |

Таймауты выше, чем у коротких однотабличных нагрузок: транзакция может записать все 30 таблиц, и среди них есть строки в несколько килобайт.

## Пример {#example}

```bash
{{ ydb-cli }} workload replication init --path replication
{{ ydb-cli }} workload replication import --path replication --rows 1000
```

Дальше на базе-приёмнике пользователь создаёт репликацию каталога. Параметры соединения и аутентификации описаны в [CREATE ASYNC REPLICATION](../../yql/reference/syntax/create-async-replication.md). Команда нагрузки этот запрос не выполняет:

```yql
CREATE ASYNC REPLICATION replication_workload
FOR `replication` AS `replication_replica`
WITH (
    CONNECTION_STRING = 'grpcs://<источник>:2135/?database=<база-источник>',
    TOKEN_SECRET_PATH = '<секрет>'
);
```

После создания экземпляра запускается запись, при необходимости с текстом ошибок:

```bash
{{ ydb-cli }} -v workload replication run \
    --path replication \
    --users 4 \
    --max-records 10 \
    --pause 100ms \
    --seconds 300
```

Снятие нагрузки:

```bash
{{ ydb-cli }} workload replication clean --path replication
```

## Вне объёма команды {#scope}

Пользователь отдельно создаёт, описывает, завершает и удаляет экземпляр асинхронной репликации. Команда не ждёт окончания первоначального сканирования и не читает лаг. Проверка совпадения реплики с источником выполняется снаружи.
