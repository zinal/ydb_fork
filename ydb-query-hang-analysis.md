# Анализ двухчасовых зависаний запросов YDB

Дата анализа: 2 октября 2026 года.

Исходный отчёт: [«Зависание коротких запросов YDB на два часа»](https://storage.yandexcloud.net/mycop1/temp/2026-10-02/ydb-query-hang-report.md).

Исследованная версия YDB: `25.3.1.ent.3`, commit `454b74b9186e1bb0fec80c65741aa72b52e54dc1`.

## Краткий вывод

Инцидент не объясняется одной новой неизвестной ошибкой.

1. Зависание операций записи с высокой вероятностью соответствует известной регрессии [#42538](https://github.com/ydb-platform/ydb/issues/42538), исправленной в [PR #43452](https://github.com/ydb-platform/ydb/pull/43452). Исправление отсутствует в `25.3.1.ent.3`.
2. Зависание чтения, начавшегося одновременно с разрывом interconnect, вероятно связано с отдельной известной ошибкой очистки после сериализации oversized event, исправленной в [PR #48532](https://github.com/ydb-platform/ydb/pull/48532). Это исправление также отсутствует в `25.3.1.ent.3`.
3. Первичным внешним триггером были недоступность записи в BlobStorage, перемещения и split DataShard. Почему storage group перешла в `BLOCKED`, по имеющимся данным определить нельзя.
4. Источник KQP-события размером более 140 МБ отчётом не установлен. Событие декодируется как `TEvStartKqpTasksRequest`. В актуальном `main` остаётся возможность сформировать aggregate request больше лимита interconnect, несмотря на ограничение размера отдельной задачи.

Таким образом, многочасовое ожидание в основном объясняется уже известными дефектами, присутствующими в используемой старой ветке, поверх отдельного сбоя хранилища.

## Исходные наблюдения

В логах обнаружено пять коротких OLTP-операций, завершившихся через ровно 7200 секунд:

- три пакетные записи;
- одна однострочная запись;
- одно точечное чтение.

Все операции начались в интервале `05:06–05:16 UTC` и завершились серверным `TIMEOUT` после срабатывания таймаута `7200000 ms`.

Инцидент сопровождался:

- ответами BlobStorage `TEvVPut status# BLOCKED`;
- длительными `TEvPut`;
- split DataShard;
- демоушенами таблеток;
- большим числом `Distributed transaction aborted due to commit failure`;
- `Outdated readset` и invalidated locks;
- разрывами interconnect с причиной `EventTooLarge`.

Эти события объясняют момент возникновения ошибки, но сами по себе не должны приводить к двухчасовому ожиданию ответа. При корректной обработке запрос должен быстро завершиться retriable-ошибкой `UNAVAILABLE`, `OVERLOADED` или `UNDETERMINED`.

## Ошибка BufferActor после перемещения шардов

### Известная проблема

[Issue #42538](https://github.com/ydb-platform/ydb/issues/42538) описывает зависание KQP после перемещения table shards. Сигнатура практически совпадает с рассматриваемым инцидентом:

- `TEvKqpBuffer::TEvError` со статусом `UNAVAILABLE`;
- session actor остаётся в `ExecuteState`;
- executer ожидает compute actor;
- compute actor ожидает завершения sink;
- forward write actor остаётся с `InFlight=true`;
- запрос завершается только по внешнему таймауту.

Проблема была исправлена в:

- основном репозитории: commit [`8d9bc03aee7`](https://github.com/ydb-platform/ydb/commit/8d9bc03aee7ffc2969e6adacac4534af5ba33164);
- PR: [#43452](https://github.com/ydb-platform/ydb/pull/43452);
- backport в `stable-26-2-1`: [#43864](https://github.com/ydb-platform/ydb/pull/43864), commit `197ea90e5e4`.

Версия `25.3.1.ent.3` собрана 11 июня 2026 года. Исправление вошло в `main` 16 июня 2026 года и потому в исследуемой версии отсутствует.

### Механизм ошибки

`TKqpTableWriteActor` отправляет операции через pipe cache и при завершении делает unlink. В неисправленной версии запоздалый `TEvDeliveryProblem` может быть обработан уже после unlink.

Он ошибочно передаётся выше как актуальная ошибка записи и переводит долгоживущий BufferActor в ошибочное состояние. Следующие операции записи в этой сессии могут отправить `TEvBufferWrite` в BufferActor, уже находящийся в `StateError`. Ответ forward write actor не формируется, после чего возникает цепочка ожиданий:

```text
session actor
  -> ждёт executer
     -> ждёт compute actor
        -> ждёт forward write actor
           -> ждёт BufferActor
```

Исправление добавляет проверку:

```cpp
if (!LinkedPipeCache) {
    // Игнорировать запоздалый TEvDeliveryProblem после unlink.
    return;
}
```

### Уточнение к исходному отчёту

В исходном отчёте утверждается, что `TKqpSessionActor::Handle(TEvKqpBuffer::TEvError)` только пересылает ошибку executer и поэтому запрос продолжает ждать.

Это описание неполно. В `25.3.1.ent.3`:

1. session actor действительно пересылает `TEvKqpBuffer::TEvError`;
2. data executer обрабатывает это событие;
3. обработчик вызывает `HandleAbortExecution`;
4. обычный путь должен сформировать ошибочный `TEvTxResponse` и завершить executer.

Следовательно, само перенаправление `TEvKqpBuffer::TEvError` не является причиной зависания. Причина известной ошибки — рассинхронизация состояния write actor/BufferActor после shard movement и запоздалого `TEvDeliveryProblem`.

### Соответствие наблюдаемым запросам

Три зависших исполнения имеют `TEvKqpBuffer::TEvError UNAVAILABLE` в начале выполнения. Это непосредственно соответствует сигнатуре #42538.

Однострочная запись без новой строки `TEvKqpBuffer::TEvError` тоже совместима с этой ошибкой: после перехода долгоживущего BufferActor в `StateError` последующая запись может зависнуть без генерации ещё одной ошибки.

Поэтому четыре операции записи с высокой вероятностью относятся к известной ошибке #42538.

## Разрыв interconnect из-за oversized event

### Точный тип события

Исходный отчёт определяет `0x10310140` только как служебное событие KQP. Код позволяет установить точный тип:

```text
ES_KQP = 4145
EventSpaceBegin(ES_KQP) = 0x10310000
EvStartKqpTasksRequest = EventSpaceBegin(ES_KQP) + 320
                       = 0x10310140
```

Следовательно, oversized event — это `TEvStartKqpTasksRequest`, запрос запуска KQP compute tasks.

Размер пользовательских параметров зависших запросов не определяет размер этого события. Оно содержит сериализованные task graph, программы задач, runtime settings и другие служебные данные.

### Ограничения размера

Лимит interconnect в `25.3.1.ent.3`:

```cpp
EventMaxByteSize = 140 << 20;
```

KQP отдельно проверяет, что каждая сериализованная задача не превышает 48 МБ. Однако один `TEvStartKqpTasksRequest` может содержать несколько задач для одной ноды. В результате:

```text
размер каждой задачи < 48 МБ
суммарный размер запроса > 140 МБ
```

Проверки aggregate-размера всего `TEvStartKqpTasksRequest` в исследованном коде нет. Такая возможность сохраняется и в текущем `main`.

### Известная ошибка очистки interconnect

В `25.3.1.ent.3` сериализация слишком большого события завершает interconnect session через `Terminate(EventTooLarge)`.

[PR #48532](https://github.com/ydb-platform/ydb/pull/48532), commit [`9f8d5a7e15d`](https://github.com/ydb-platform/ydb/commit/9f8d5a7e15d92924aa2959fc6b8c5013c7142c6a), исправляет очистку после этого исключения:

- oversized event возвращается отправителю как `TEvUndelivered`;
- активная сериализация корректно отменяется;
- после восстановления соединения обычные события снова доставляются.

Регрессионный тест из этого PR проверяет событие размером `EventMaxByteSize + 1`, получение `Undelivered` и успешную доставку следующего сообщения.

Исправление вошло в `main` 6 августа 2026 года, но не было backport-ировано в стандартные релизы до `26.3.1.ent.3` включительно.

### Связь с зависшим чтением

Точечное чтение началось в ту же миллисекунду, когда разорвалась interconnect session `50002 <-> 50003`. Это даёт сильную временную связь.

В `TEvStartKqpTasksRequest` устанавливается `FlagTrackDelivery`. При исправленной обработке oversized event executer должен получить `TEvUndelivered` и быстро вернуть `UNAVAILABLE`. В старой версии очистка и nondelivery могли не завершиться корректно.

Поэтому зависшее чтение, вероятнее всего, связано с известной ошибкой #48532. Без полных actor logs это заключение имеет меньшую уверенность, чем сопоставление записей с #42538.

Обработчик `HandleDisconnected` сам по себе не доказывает дефект: уже запущенные remote compute actors могут пережить кратковременный разрыв TCP session и продолжить работу после reconnect. Критична потеря корректного `Undelivered` для события, которое фактически не могло быть сериализовано.

## Почему проблема не проявлялась на 25.2.1.ent.13

Наблюдение о стабильной работе `25.2.1.ent.13` согласуется с историей кода.

В `25.2.1.ent.13` отсутствуют изменения, сформировавшие уязвимый механизм:

- [PR #18720](https://github.com/ydb-platform/ydb/pull/18720), `Streaming write to index (INSERT)`;
- [PR #19300](https://github.com/ydb-platform/ydb/pull/19300), `Refactor write actor buffers`.

В частности, в `25.2.1.ent.13` нет используемых в проблемном пути `StateError` и `LinkedPipeCache`. Они присутствуют в `25.3.1.ent.3`, но ещё без проверки из #43452.

Таким образом, #42538 является регрессией ветки 25.3 относительно исследованной 25.2, а не просто редко проявлявшейся общей ошибкой старых версий.

Это не означает, что 25.2 содержит исправление #43452: соответствующий кодовый путь в ней устроен иначе, поэтому исправление в такой форме ей не требуется.

| Ветка | Наличие исправления |

| `25.2.1.ent.13` | Исправления нет; уязвимый механизм 25.3 отсутствует |
| `25.3.1.ent.1–ent.3` | Нет |
| `25.4.1.ent.1–ent.2` | Нет |
| `26.1.1.ent.1–ent.3` | Нет |
| `26.2.1.ent.1+` | Есть |
| `26.3.1.ent.1+` | Есть |
| `main` после 16.06.2026 | Есть |

Для обычных, не Enterprise, сборок:

- первая исправленная версия 26.2 — `26.2.1.4`;
- все проверенные версии `26.2.1.4+` содержат исправление;
- ветка 26.3 содержит исправление начиная с `26.3.1.1`.

### Исправление oversized event cleanup, #48532

На момент анализа commit `9f8d5a7e15d` присутствует в `main`.

Он отсутствует в проверенных стандартных релизах:

- `26.2.1.14`;
- `26.2.1.ent.4`;
- `26.3.1.18`;
- `26.3.1.ent.3`.

Следовательно, обновление до 26.2 или 26.3 закрывает зависание BufferActor, но само по себе не гарантирует наличие исправления interconnect #48532.

## Роль BlobStorage и DataShard

Состояние storage group `BLOCKED`, длительные `TEvPut`, split и демоушены DataShard были триггером известных ошибок:

1. write actors получили delivery failures во время перемещения шардов;
2. началась лавина aborted distributed commits и retries;
3. один из KQP executer сформировал oversized `TEvStartKqpTasksRequest`;
4. разрыв interconnect увеличил радиус воздействия.

При этом имеющихся данных недостаточно, чтобы определить первопричину перехода storage group `2181038087` в `BLOCKED`. Возможны как аппаратные/дисковые проблемы, так и административные операции или защитные состояния BlobStorage.

`commit failure`, `Outdated readset` и invalidated locks являются преимущественно последствиями сбоя и перемещений, а не самостоятельным объяснением двухчасового ожидания.

## Итоговая классификация

| Наблюдение | Классификация | Уверенность |
|---|---|---|
| Три записи с `TEvKqpBuffer::TEvError UNAVAILABLE` | Известная исправленная ошибка #42538/#43452 | Высокая |
| Запись без новой BufferActor error | Совместима с зависанием следующей записи в уже ошибочном BufferActor | Высокая/средняя |
| Чтение в момент `EventTooLarge` | Вероятно известная исправленная ошибка #48532 | Средняя |
| Storage group `BLOCKED` | Отдельный инфраструктурный или BlobStorage-инцидент | Причина не установлена |
| `TEvStartKqpTasksRequest` > 140 МБ | Отдельная проблема формирования aggregate KQP event | Не исправлена/не идентифицирована |

## Рекомендации

1. Для устранения основного зависания write path использовать как минимум `26.2.1.ent.1` или `26.3.1.ent.1`.
2. Проверять наличие конкретного backport-коммита `197ea90e5e4`, а не только номер patch-релиза.
3. Для покрытия interconnect-сценария отдельно backport-ировать `9f8d5a7e15d` либо использовать будущий релиз, в котором подтверждено его наличие.
4. Установить для коротких OLTP-операций операционный таймаут значительно меньше 7200 секунд. Это не исправляет серверную ошибку, но уменьшает пользовательский эффект потерянного пути завершения.
5. Добавить диагностику размера `TEvStartKqpTasksRequest` до отправки:
   - TxId;
   - количество задач;
   - размер каждой задачи;
   - aggregate serialized size;
   - target node.
6. Ввести проверку aggregate serialized size до передачи события в interconnect и возвращать контролируемый `LIMIT_EXCEEDED`.
7. Отдельно расследовать причины `BLOCKED` для storage group `2181038087` по состоянию PDisk/VDisk, quorum, donor/slay/restart операциям и административным событиям.

## Ограничения анализа

Анализ выполнен по агрегированному отчёту, исходному коду и истории публичного репозитория YDB. Полные сырые логи, actor dumps и содержимое oversized event недоступны.

Поэтому:

- сопоставление write hangs с #42538 подтверждается кодом и практически идентичной сигнатурой;
- связь point read с #48532 вероятна, но не доказана до уровня конкретного sender actor;
- источник oversized `TEvStartKqpTasksRequest` не установлен;
- причина перехода BlobStorage group в `BLOCKED` не установлена.
